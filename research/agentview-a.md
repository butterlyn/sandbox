## Summary
- Screen: HOLD (A1, A3, A4).
  - The hold is structural, the same as claude-desktop's. Agent view runs only Claude Code sessions, so under 7.4 and 7.6 it needs a Codex partner for A1, A3 and A4.
  - N3, N2 and C1 PASS. N1 does not apply (closed source).
- **Deep-dive (2026-10-19):** add-on to claude-desktop.
  - Component-level ALWAYS gates: A2 PASS; A6 (both directions), A7 and A8 (both directions) PASS (workaround); A5 FAIL (adds nothing); A1, A3, A4 stay PARTIAL (structural, Claude-only).
  - FAVOUR: F1–F10 = 7/20, F11a–e = 5/10.
  - Most useful fact: `claude --bg` + `claude agents --json` + `claude --resume <id> --bg` make Codex → Claude delegations first-class, monitorable background sessions (documented for "another Claude session that supervises background work"), better than headless `claude -p`. Phone visibility depends on Remote Control, whose link drops on every supervisor restart (#103264).
- **Preview label (7.16a).** Agent view has been a "research preview" since 2.1.139 (2026-05-11), but it ships switched on in the stable build: `disableAgentView` defaults to unset, "so agent view is available". That makes the label a caveat, not an opt-in flag. Under the strict alternative, C1 would also become PARTIAL.
- **PC side.** Agent view runs on native Windows (the supervisor is started through PowerShell so it outlives the terminal) and in WSL2 (the docs describe Linux/WSL behaviour).
  - The supervisor is a background process that starts on demand. It has no documented boot-time service. A reboot stops sessions, which can be resumed afterwards.
  - Windows 10 has open input bugs in attached sessions (ConPTY).
- **iPhone side.** Background sessions can join Remote Control, either with `claude --bg … --remote-control` or through `remoteControlAtStartup`. They then appear in the Claude iOS app.
  - The evidence for this is changelog entries and issues only. The agent-view docs never mention Remote Control or mobile.
  - An open bug drops the Remote Control link on every supervisor restart, including auto-updates.
  - The app cannot dispatch a new agent-view session with a chosen directory; it can only fork an existing session.
  - All of (i)–(iii) are possible only through 7.4's generic-terminal path running `claude agents`.
- **Fit.** This is a Claude-side add-on to claude-desktop, not a standalone hub. Its most useful contribution is `claude agents --json`, which reports each session's state for A8 monitoring of Claude sessions.

## Open questions
- **Does auto-connect cover dispatched sessions?** Does `remoteControlAtStartup: true` reliably connect sessions dispatched from inside agent view, not only those started with `claude --bg --remote-control`? Only issue #103264 shows it; no doc states it.
  - Affects: the Claude half of A1(i)/(ii) and F11e. A docs statement would settle it.
- **Will #103264 be fixed?** Until it is, phone access to long-lived background sessions breaks after every auto-update.
  - Affects: the reliability of A1(i)/(ii) on the Remote Control path. A fix would leave only (iii) and Codex missing on that path.
- **Which permission dialogs reach the app?** Are other permission dialogs from `--bg` sessions relayed to the Claude app? Only EnterWorktree is confirmed missing (#96490).
  - Affects: A1(ii) on the Remote Control path.
- **Can the app start a fresh session?** Can the Claude app start a fresh agent-view session in a chosen directory? Today it can only fork (2.1.273).
  - Affects: A1(iii) on the Remote Control path. Without it, (iii) needs either a screened terminal app (generic-terminal path) or claude-desktop's Remote Control server mode, whose sessions are not agent-view sessions.
- **Is a Codex shell job fully interactive?** Does attaching to a `!codex` or `claude --bg --exec 'codex …'` PTY job give a fully interactive Codex TUI on Windows and WSL2? The changelog says only "attach to and detach from".
  - Affects: no gate (A3/A4 stay PARTIAL because the job is not first-class), but it bears on F5 and F11d for Codex.
- **Does WSL2 keep the supervisor alive?** Does the WSL2 distro keep running with no terminal open on the always-on PC?
  - Affects: the C1 "unattended" note, not the verdict. A Microsoft WSL lifecycle source is needed.
- **Is the PC on Windows 10 or Windows 11?** The ConPTY input bugs (#99659, #103327) are reported on Windows 10. If the user is on Windows 10, running agent view inside WSL2 may avoid them.
  - Affects: the C1 caveat and day-to-day use of `claude attach` on native Windows.

### Harness integration
- **Source is unavailable.** Claude Code is closed; anthropics/claude-code holds the changelog only. Everything here is from Anthropic's docs and changelog.
- **Supervisor:** started on demand by `claude agents` or `claude --bg`; on native Windows "through PowerShell so the service survives closing the terminal". Each session is "its own Claude Code process under the supervisor"; idle unattached sessions are stopped after about an hour and resume on attach or reply; after an auto-update the supervisor "restarts itself onto the new version". No boot-time service is documented; a reboot stops sessions (they resume from disk on attach or reply).
- **`claude --bg "<prompt>"`:** a full interactive-capable session in the background; `--bg` with `-p` is rejected. `--agent`, `--name`, `--resume <id>` (in place on v2.1.257+) and `--fork-session` combine with it. Non-interactive dispatch needs a pre-trusted directory.
- **`claude --bg --exec '<command>'` / `!<command>`:** a PTY job with no model; output in memory; row removed ~5 minutes after exit.
- **`claude agents --json [--all] [--cwd <path>]`:** the documented machine interface (state, status, waitingFor, sessionId).
- **Remote Control:** not in the agent-view docs. Evidence: `--remote-control` survives retire→wake (2.1.169); `remoteControlAtStartup` applies to "each interactive session"; background sessions joined to RC appear in the Claude apps. Defect: the RC link is lost on every supervisor restart including auto-updates (#103264, open; 2.1.303 lists no fix).
- **Credentials:** the supervisor reads Claude Code's own stored login; it forwards gateway variables only under documented conditions. No third-party read, copy or proxy, so no 7.16b note.

### Stack fit
- **Role:** a Claude-side add-on to claude-desktop in the Windows-native topology (T-W). It does not change any gate verdict at stack level, but it upgrades two things:
  - **Codex → Claude delegation:** use `claude --bg` + `claude agents --json` + `claude --resume <id> --bg` instead of headless `claude -p`. Children become first-class sessions with state, appear in agent view, open in the TUI, and (with `remoteControlAtStartup: true`) can show on the iPhone, which headless `-p` children cannot (claude-desktop F11e).
  - **Claude-side monitoring for any supervisor:** `claude agents --json` gives `blocked`/`waitingFor` without parsing transcripts.
- **Partners:** chatgpt-desktop-codex for Codex (A1/A3/A4); a file-visibility partner for A5/F7/F8; Tailscale for F6.
- **Conflicts and caveats:**
  - Two session systems: sessions started from the phone through Remote Control server mode are not agent-view sessions (#98788, #95581), so the phone and agent view see different lists.
  - #103264: every supervisor restart (including auto-updates) drops the RC link, so phone access to long-lived background sessions needs a re-connect after each update.
  - Codex children dispatched as `--exec` jobs vanish from the list ~5 minutes after exit; their record lives only in `~/.codex/sessions`.
  - On Windows-native Codex, a sandboxed `claude --bg` call may need approval to reach the supervisor (the claude-desktop deep-dive found Codex → Claude calls need approval because Codex's sandbox blocks network); unverified for the supervisor's named pipe.
  - Windows 10 ConPTY bugs (#99659, #103327) affect `claude attach` on native Windows.
  - Quota: "running ten agents in parallel uses quota roughly ten times as fast".
