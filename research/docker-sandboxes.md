## Summary
- Screen: SCREEN HOLD (A1, A3)
- Deep-dive: component-level A2 PASS, A7 PASS (workaround); A5 FAIL (needs partner); A6, A8 and A3 PARTIAL (only Claude children qualify); FAVOUR F1–F10 6/20, F11a–e 2/10. Use only as an optional isolation layer for *Claude* sessions, with workspaces on host paths and transcripts copied out before `sbx rm`.
- Correction (2026-10-19, deep-dive): A3 (Codex, local) is **FAIL on every documented path**, not PARTIAL. The documented OAuth mode is the 7.6 "externally managed ChatGPT tokens" row, which passes "only with OpenAI-documented consent … else FAIL". No OpenAI source covers `sbx`'s flow: it is neither Codex app-server authentication nor Sign in with ChatGPT plan sharing. The only possible routes out are undocumented and untested (in-sandbox `codex login` in the kit's "none" mode, or a custom kit with `oauth.passthrough: true`), so they are UNKNOWN. The component's overall A3 stays PARTIAL because the Claude path passes.
- **Status.** Active and closed source. Docker shipped 34 stable `sbx` releases between 2026-03-31 and 2026-10-13. The older Docker Desktop `docker sandbox` plugin was removed in Desktop 4.80.0 (2026-06-29) with "Migrate to `docker sbx`". N1 does not apply; N2 and N3 pass.
- **Windows (C1).** `sbx` installs natively on Windows 11 (winget or MSI). It needs Windows Hypervisor Platform, not Docker Desktop or WSL2. Docker staff call the Linux build inside WSL2 "best-effort". Windows 10 is not a supported platform.
- **Phone access (A1).** `sbx` has no phone UI of its own. Sandboxed sessions can be reached through partner components, so A1 is not a hard fail:
  - Claude: Anthropic Remote Control, which Docker documents and allowlists. Remote Control server mode is broken (#695), so the phone cannot start new sandboxed sessions.
  - Codex: an SSH connection from the ChatGPT desktop app to the sandbox, used from ChatGPT on iOS.
  - Both: an iOS SSH terminal app with tmux on the PC.
- **Harnesses (A4).** Both harnesses are the official, unmodified binaries, so A4 passes.
- **Subscriptions (A3)** is where this candidate is weak. In every path, `sbx` handles the plan tokens itself:
  - Claude: the user signs in with Claude Code's own `/login`. `sbx`'s TLS-intercepting proxy then captures, stores and refreshes the Claude OAuth tokens, and injects them in transit. Under the 7.16b main rule this is a PASS with a mandatory policy-risk note. Under the strict alternative it is a FAIL.
  - Codex: `sbx` runs its own ChatGPT sign-in, using the Codex CLI's OAuth client ID, and points Codex at a custom provider. OpenAI's consent covers "local or open-source" apps and excludes "commercial or hosted services", which leaves Docker's case unclear, so the Codex path is PARTIAL.
  - Cloud sandboxes: FAIL for both harnesses, so the stack must avoid them.
- **Transcripts.** They live inside the sandbox and are deleted by `sbx rm`. This matters for A6b.

**Credential-handling policy risk (7.16b, required).**
- **Anthropic's policy:** "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." The same page also says that this does not "prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code" (https://code.claude.com/docs/en/legal-and-compliance, undated, retrieved 2026-10-19).
- **What `sbx` does locally:** the sign-in completes in Claude Code's own `/login`. After that, the host proxy (TLS-intercepting: "intercepted HTTPS connection" in the v0.48.0 notes; the binary carries "Docker Sandboxes Proxy CA") does the following:
  - captures the token response from `platform.claude.com/v1/oauth/token`;
  - keeps the real access and refresh tokens in the host secret store;
  - hands Claude Code sentinel tokens;
  - substitutes the real token on every request to Anthropic;
  - refreshes the tokens itself with Claude Code's OAuth client ID `9d1c250a-e61b-44d9-88ed-5944d1962f5e`. That is the same `CLIENT_ID` found in Claude Code 2.1.303, `@anthropic-ai/claude-code-linux-x64`, published 2026-10-18. Binary strings: "oauth: refreshed anthropic oauth access token", "oauth: token manager captured primary api key".

  This is collecting, storing and intermediating Claude.ai session tokens, though only on the user's own machine.
- **Cloud is worse:** `sbx --cloud secret set anthropic --oauth` is a Claude sign-in run by `sbx`, and its tokens are stored on Docker's servers.
- **Anthropic does mention the product:** its sandbox page lists Docker Sandboxes as "a free, standalone product from Docker" for running Claude Code (https://code.claude.com/docs/en/sandbox-environments, undated). It does not mention the token handling, and no Anthropic approval of it was found.
- **OpenAI:** `sbx` signs in as the Codex CLI's own OAuth client, which is client impersonation, and the cloud variant keeps ChatGPT tokens on Docker's servers. OpenAI's own text is quoted in the A3 (Codex) row.

### Harness integration (docs and embedded kits; no public source)
- **How it invokes `claude`:**
  - Template `claude-code-docker` installs the official binary (`claude.ai/install.sh`).
  - The default start is `claude --dangerously-skip-permissions`.
  - Headless use is `sbx exec X -- claude -p …`.
  - Claude Code's default prompt and tools are kept (A4 PASS, 7.16d).
- **How it invokes `codex`:**
  - Template `codex-docker` installs `@openai/codex`.
  - The default start is `codex --dangerously-bypass-approvals-and-sandbox`, and the kit writes `approval_policy = "never"` and `sandbox_mode = "danger-full-access"`.
  - In OAuth mode the kit adds `forced_login_method = "api"` and the `sandboxd` model provider (base_url `chatgpt.com/backend-api/codex`, sentinel bearer). Codex's built-in prompt is untouched (A4 PASS).
- **OAuth credentials:**
  - Claude: captured by the host proxy from Claude Code's own `/login`, then stored, refreshed and injected (screen).
  - Codex: obtained by `sbx`'s host-side flow under the Codex CLI's client ID, then stored and injected.
  - The only documented opt-out is a kit's `oauth.passthrough: true`, which "reduces credential isolation". The built-in kits don't use it.
- **Credential-handling policy risk (7.16b): still applies.** The screen note stands. In addition:
  - The proxy enforces which OAuth grants are allowed ("rejects unrecognized OAuth token grants and prevents their responses from replacing host-managed credentials", v0.47.0).
  - The proxy is TLS-intercepting, so even a passthrough setup carries tokens through `sbx`'s proxy in clear text on the host.
- **Transcript locations:** inside the VM, at `/home/agent/.claude/projects` (on its own volume) and `/home/agent/.codex`. Both are deleted by `sbx rm`.

### Stack fit
- **Layer:** runtime/sandbox only. It needs partners for A1 (Claude app via Remote Control, or an orchestrator over SSH), A5 (host-side SMB over Tailscale), A2 after teardown (agentsview on exported transcripts) and A8 orchestration (a host-side agent or orchestrator).
- **Topology that works on this PC:**
  - Windows 11 with Windows Hypervisor Platform, and `sbx` installed natively (`winget install -h Docker.sbx`). The WSL2 build is "best-effort", and Windows 10 is unsupported.
  - Repos on `C:\`, mounted in direct mode, so the Tailscale SMB path (A5) and the Windows-native Claude and Codex desktop apps see the same files.
  - Use `sbx` only for *Claude* sessions that need isolation, launched by a host-side agent or orchestrator with `sbx create` / `sbx exec`, or interactively with `sbx run --name X claude -- --remote-control "X"` after `sbx settings set claude.remoteControl true` for iPhone access.
  - Run Codex unsandboxed on the host.
  - Put a project-level `.claude/settings.json` (raised `cleanupPeriodDays`, plus a Stop hook copying `transcript_path` into the mounted repo) in each repo used in sandboxes.
- **Orchestrator integration:**
  - Documented SSH targets: VS Code, Cursor, Claude Desktop, ChatGPT and T3 Code.
  - T3 Code "treats the sandbox as an ordinary SSH host … starts a T3 server inside". Its Codex path there inherits `sbx`'s Codex auth (FAIL). The `t3code` kit lives in `docker/sbx-kits-contrib` (177★, fails N1), so install manually instead.
  - Orca, Maestro, Archon, Agor and Gas City have no documented integration; Orca's SSH runtimes against `*.sbx` are untested.
  - Remote Control server mode inside `sbx` is broken on stable (#695), so the phone cannot start sandboxed sessions.
- **Conflicts and costs:**
  - A Docker account is required (`sbx login`), and telemetry is on by default (`SBX_NO_TELEMETRY` to opt out).
  - Agents run with approvals bypassed inside the VM ("Inside the VM, the agent has full privileges").
  - Host user-level Claude/Codex config and hooks are not imported.
  - Docker's get-started page names "Max, Team, or Enterprise" for subscription sign-in, while the Claude agent page doesn't restrict plans; Pro is unconfirmed.
