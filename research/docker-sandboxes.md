## Summary
- Screen: SCREEN HOLD (A1, A3)
- **Status.** Active and closed source. Docker shipped 34 stable `sbx` releases between 2026-03-31 and 2026-10-13. The older Docker Desktop `docker sandbox` plugin was removed in Desktop 4.80.0 (2026-06-29) with "Migrate to `docker sbx`". N1 does not apply; N2 and N3 pass.
- **Windows (C1).** `sbx` installs natively on Windows 11 (winget or MSI). It needs Windows Hypervisor Platform, not Docker Desktop or WSL2. Docker staff call the Linux build inside WSL2 "best-effort". Windows 10 is not a supported platform.
- **Phone access (A1).** `sbx` has no phone UI of its own. Sandboxed sessions can be reached through partner components, so A1 is not a hard fail:
  - Claude: Anthropic Remote Control, which Docker documents and allowlists. Remote Control server mode is broken (#695), so the phone cannot start new sandboxed sessions.
  - Codex: an SSH connection from the ChatGPT desktop app to the sandbox, used from ChatGPT on iOS.
  - Both: an iOS SSH terminal app with tmux on the PC.
- **Harnesses (A4).** Both harnesses are the official, unmodified binaries, so A4 passes.
- **Subscriptions (A3)** is where this candidate is weak. In every path, `sbx` handles the plan tokens itself:
  - Claude: the user signs in with Claude Code's own `/login`. `sbx`'s TLS-intercepting proxy then captures, stores and refreshes the Claude OAuth tokens, and injects them in transit. Under the 7.16b main rule this is a PASS with a mandatory policy-risk note. Under the strict alternative it is a FAIL.
  - Codex: `sbx` runs its own ChatGPT sign-in, using the Codex CLI's OAuth client ID, and points Codex at a custom provider. OpenAI's consent covers "local or open-source" apps and excludes "commercial or hosted services", which leaves Docker's case unclear, so the Codex path is PARTIAL.
  - Cloud sandboxes: FAIL for both harnesses, so the stack must avoid them.
- **Transcripts.** They live inside the sandbox and are deleted by `sbx rm`. This matters for A6b.

**Credential-handling policy risk (7.16b, required).**
- **Anthropic's policy:** "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." The same page also says that this does not "prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code" (https://code.claude.com/docs/en/legal-and-compliance, undated, retrieved 2026-10-19).
- **What `sbx` does locally:** the sign-in completes in Claude Code's own `/login`. After that, the host proxy (TLS-intercepting: "intercepted HTTPS connection" in the v0.48.0 notes; the binary carries "Docker Sandboxes Proxy CA") does the following:
  - captures the token response from `platform.claude.com/v1/oauth/token`;
  - keeps the real access and refresh tokens in the host secret store;
  - hands Claude Code sentinel tokens;
  - substitutes the real token on every request to Anthropic;
  - refreshes the tokens itself with Claude Code's OAuth client ID `9d1c250a-e61b-44d9-88ed-5944d1962f5e`. That is the same `CLIENT_ID` found in Claude Code 2.1.303, `@anthropic-ai/claude-code-linux-x64`, published 2026-10-18. Binary strings: "oauth: refreshed anthropic oauth access token", "oauth: token manager captured primary api key".

  This is collecting, storing and intermediating Claude.ai session tokens, though only on the user's own machine.
- **Cloud is worse:** `sbx --cloud secret set anthropic --oauth` is a Claude sign-in run by `sbx`, and its tokens are stored on Docker's servers.
- **Anthropic does mention the product:** its sandbox page lists Docker Sandboxes as "a free, standalone product from Docker" for running Claude Code (https://code.claude.com/docs/en/sandbox-environments, undated). It does not mention the token handling, and no Anthropic approval of it was found.
- **OpenAI:** `sbx` signs in as the Codex CLI's own OAuth client, which is client impersonation, and the cloud variant keeps ChatGPT tokens on Docker's servers. OpenAI's own text is quoted in the A3 (Codex) row.

## Open questions
- **C1: the user's Windows version.** `sbx` lists Windows 11 only, and WSL2 nested virtualization is also Windows 11 only. On Windows 10, C1 becomes FAIL.
- **A3 Codex: OpenAI's consent.** No OpenAI source names Docker Sandboxes. Two things would settle it:
  - an OpenAI statement or partner listing covering Docker's use of the Codex CLI's OAuth client, or Docker moving to Sign in with ChatGPT. Either would make it PASS.
  - OpenAI treating Docker as a "commercial … service". That would make it FAIL.
- **A3 Codex: a cleaner path?** The kit's "none" mode "deliberately permits login", and OpenAI documents copying `auth.json` into a Docker container. Untested: whether the proxy (whose kit intercepts `auth.openai.com /oauth/token`) leaves a native `codex login --device-auth` or a copied `auth.json` alone. If it does, Codex would sit on the 7.6 "unmodified codex … managed ChatGPT login" PASS row.
- **A3 Claude: a path without interception?** Two candidates are untested:
  - a user-minted `CLAUDE_CODE_OAUTH_TOKEN` passed with `sbx run -e`. The binary references the variable, but the behaviour is undocumented.
  - the Claude Desktop SSH path.

  If the proxy left the token untouched, Claude would sit on the 7.6 setup-token row (A3 PASS, F1 PARTIAL) with no intermediation.
- **7.16b scope.** `sbx` "offers its own claude.ai login" in its cloud path. This screen grades each path (7.6 "Grade every harness path"). Applied to the whole platform, that clause would make A3 FAIL for Claude, and the screen would become SCREEN FAIL at A3.
- **A1 (iii) for Claude.** Remote Control server mode (#695) is still broken. A fix would let the phone start sandboxed Claude sessions.
- **A1 for Codex.** It is unconfirmed that ChatGPT on iOS can list and start chats on a Docker-sandbox SSH host attached to the Windows desktop app.
- **A6b.** There is no documented way to keep `~/.claude/projects` or `~/.codex` on host storage past `sbx rm`. Pointing `CLAUDE_CONFIG_DIR` or `CODEX_HOME` at a mounted workspace is untested. Without one of these, sandboxed delegation is FAIL or UNKNOWN for A6b.
- **Plan coverage.** Docker's page names "Max, Team, or Enterprise" for Claude subscription sign-in. Pro is not mentioned.
- **Contrib kits.** If the stack depends on `docker/sbx-kits-contrib` kits (e.g. the `t3code` kit), that repo has 177★ and fails N1 as its own component.
