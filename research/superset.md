## Summary
- Screen: SCREEN HOLD (C1)
- **C1 (user assumption, 2026-10-19): `PASS (user assumption)`** per brief 7.18 ("Assume superset can run on windows via WSL2 installation"). The vendor's own caveats stand as risks, not failures:
  - no Windows build;
  - the Linux desktop app is "experimental and untested";
  - the host CLI is "currently in Beta", with Pre-release-flagged releases;
  - a maintainer says WSL support is "not at least for a few months" (#1993);
  - the vendor's comparison page tells Windows/WSL users to choose a competitor.
- **Deep-dive (2026-10-19, deepdive-superset).** Topology: the standalone CLI host in WSL2, plus the Superset iOS/iPadOS app over Superset's relay.
  - **PASS:** A1, A2, A3, A4, A6, A8, and C1 (user assumption).
    - A3 carries the 7.16b policy-risk note and three 7.16c conditions: no cloud workspaces, no agent sign-ins stored in Superset cloud, and always `--local`/`--host`.
    - A4 PASS is for the terminal path. Superset Chat's Claude path is A4 PARTIAL under 7.16d, so avoid it.
    - A8 is first-class in both directions, through `superset agents create/wait/read` and `terminals read/send`.
  - **A7:** `PASS (workaround)`; the separate-sandbox clause is not exercised.
  - **A5:** PARTIAL. iOS opens changed files only, with no full tree.
  - **FAVOUR:** F1–F10 = 11/20; F11a–e = 8/10.
- **Resolved screen open question.** Can a CLI-only host be reached from the phone? Yes. The docs say `superset start --daemon` "registers the machine with the relay so other clients in your organization can find it" ([remote-access.mdx#L40](https://github.com/superset-sh/superset/blob/8bc96462cc6b08c5fff5f812305c2cf29ea826cf/apps/docs/content/docs/remote-access.mdx#L40), at 8bc9646, 2026-10-18).
- **N1–N3 pass.** The project is healthy and run by a team:
  - 15.3k★ under ELv2, with desktop releases every few days.
  - Two humans each wrote about 41% of non-bot commits since 2026-04-22.
  - Two different maintainers merge outside contributors' PRs.
- **C1 is the blocker.**
  - No Windows build: "Windows is planned with no date".
  - The Linux desktop app is "experimental and untested".
  - A maintainer said WSL support is "not at least for a few months".
  - The vendor's own comparison page tells people who work "on Windows or in WSL" to choose a competitor.
- **C1, nearest pass.** The headless host server (`superset start --daemon`, with a documented systemd unit) installs officially on Linux x64/arm64 through the standalone CLI. It could therefore run unattended in WSL2. However:
  - The docs say "The CLI is currently in Beta", and the CLI's GitHub releases are flagged Pre-release, so it is PARTIAL under §5.
  - If the orchestrator reads 7.9's CLI row as overriding the Beta label, C1 becomes `PASS (via WSL2)`. That covers only this headless topology, and leaves the PC with CLI/TUI only and no supported GUI.
- **A1 passes.** The App Store iPhone/iPad app (1.1.3, native iPad layouts) does all three A1 tasks for both Claude Code and Codex:
  - lists hosts and sessions, and streams their terminals;
  - sends input, including esc/arrow/enter keys;
  - starts a Claude Code or Codex session in a chosen project and branch on a chosen host.
  - Requirements: **Superset Pro** ($20/user/month, or $15 billed yearly) and **iOS/iPadOS 26+**.
  - It reaches the PC only through Superset's vendor-hosted relay, a Cloudflare Worker at relay.superset.sh. No self-hosting is documented, and no end-to-end encryption was found in the relay source.
- **A3/A4 pass on the self-hosted path.** Terminal agents run the unmodified `claude` and `codex` binaries under the host's own logins.
  - The stack must avoid cloud workspaces (a Pro feature). They run on Vercel Sandbox; Claude there uses a stored `claude setup-token` token, and Codex appears to be API-key only.
  - Flags for the deep-dive:
    - the quota meter and desktop dictation read stored OAuth tokens (affects F1);
    - Superset Chat runs on the Claude Agent SDK and `codex app-server`.

## Open questions
- **C1: does the Beta label count?**
  - 7.9 says "CLI, daemon or server with an official Linux install = PASS (via WSL2)" and attaches the experimental/beta condition only to GUI apps.
  - §5 says "preview/beta only" is PARTIAL.
  - Superset's only unattended PC path is the Beta CLI host. An orchestrator ruling flips C1 between PARTIAL and `PASS (via WSL2)`. The vendor dropping the Beta label or shipping a non-experimental Linux or Windows desktop build would also settle it.
- **C1/A1: does the iOS app see a CLI-only host?**
  - The docs' iPhone steps describe only the desktop "Allow remote access" toggle.
  - The CLI host "registers the machine with the relay so other clients in your organization can find it", and the iOS app lists the org's `host.roster`. So the source says yes, but no doc confirms it for a headless host.
  - Why it matters: if a CLI-only host is not reachable, the WSL2 topology loses A1 and C1 stays PARTIAL.
- **C1: does the host run unattended in WSL2?**
  - Superset documents systemd units and, for `hosts add`, needs a valid `/etc/machine-id` and lingering. Keeping a WSL2 distro alive on an always-on PC needs Windows-side setup.
  - Superset documents neither for WSL. This affects the "runs unattended" note and how reliably the PC can be reached from the phone.
- **A3 (cloud path, 7.13): can the org turn cloud workspaces off, or does every agent/CLI call have to pass `--local`/`--host`?**
  - CLI commands default to cloud when the account "has cloud workspaces".
  - In the cloud path, Claude runs on Superset/Vercel infrastructure with a stored token, and Codex appears to be API-key only (as of commit 8bc9646).
  - If the stack can't reliably avoid cloud workspaces, A3 drops to PARTIAL/FAIL.
- **F1/A3 (deep-dive): can the token-reading features be disabled?**
  - The Usage quota meter reads the Claude OAuth token (Keychain or `~/.claude/.credentials.json`) and the Codex token (`$CODEX_HOME/auth.json`). It calls undocumented endpoints (`api.anthropic.com/api/oauth/usage`, `chatgpt.com/backend-api/wham/usage`); see https://github.com/superset-sh/superset/blob/8bc96462cc6b08c5fff5f812305c2cf29ea826cf/packages/host-service/src/trpc/router/usage/claude.ts#L1-L30.
  - Desktop dictation takes the Codex bearer token from `codex app-server` and calls `chatgpt.com/backend-api/transcribe`.
  - Both conflict with F1's "never reads, copies or proxies tokens" and may raise provider-terms questions.
- **A3/A4 (deep-dive): how does Superset Chat grade under 7.6?**
  - Claude runs through the Claude Agent SDK `query()` with `pathToClaudeCodeExecutable`; Codex through `codex app-server --stdio`, plus the claude-agent-acp and codex-acp adapters.
  - To check: the system prompt preset, the tool set, and Anthropic's current policy on Agent SDK subscription use.
  - It is avoidable if the stack uses only terminal agents.
- **Relay trust (A1 path; 7.6 relay note).** relay.superset.sh is run by the vendor; no self-hosting is documented and no end-to-end encryption was found in apps/relay.
  - Credentials stay on the PC, so A3 is unaffected.
  - But terminal I/O and host API calls pass through Superset's Worker in a form it can read. A documented self-hosted or end-to-end mode would remove this caveat.

### Harness integration (from source)
- **How it invokes `claude`.** A terminal preset runs `claude --dangerously-skip-permissions`, with `--resume` / `--fork-session` and `claude --strict-mcp-config -p` for non-interactive use. A wrapper ends in `exec "$REAL_BIN" "$@"`, and Superset adds hook entries to `~/.claude/settings.json`. Optional Superset Chat uses Agent SDK `query()` with the user's `claude` binary (`pathToClaudeCodeExecutable`), with no `systemPrompt` and `settingSources: []`, which is 7.16d PARTIAL.
- **How it invokes `codex`.** A terminal preset runs `codex --dangerously-bypass-approvals-and-sandbox --dangerously-bypass-hook-trust`, plus `resume` / `fork` / `codex exec --skip-git-repo-check`, through a wrapper that adds `--enable hooks`. Optional Chat uses `codex app-server --stdio` `thread/start` without an instruction override.
- **OAuth credentials.**
  - **Reads (local):** the usage meter reads the Claude and Codex tokens; desktop dictation reads the Codex bearer from app-server.
  - **Never** copies or proxies tokens for inference on the local path.
  - **Cloud path (avoid):** the user may upload a `claude setup-token` token or API key to Superset for cloud workspaces, where it is swapped into Authorization headers at Superset's sandbox firewall (Screen cloud row).
- **Credential-handling policy risk (7.16b).** Anthropic: "developers may not collect, store, or intermediate Claude.ai credentials or session tokens" (https://code.claude.com/docs/en/legal-and-compliance, undated, retrieved 2026-10-19).
  - Whenever the desktop app shows an agent terminal or Settings → Usage, Superset's host service reads the user's Claude OAuth access token from the Keychain or `~/.claude/.credentials.json`. It sends that token, with Claude Code's OAuth `anthropic-beta` header, to the undocumented `api.anthropic.com/api/oauth/usage` and `/api/oauth/profile`.
  - It sends the ChatGPT token to `chatgpt.com/backend-api/wham/usage` (and `/transcribe` for dictation).
  - No spoofed user-agent was found; requests use Node's default.
  - No token is sent to Superset's own servers on the local path.
  - A WSL2 headless host with only the iOS client never triggers these reads, because the iOS app makes no usage calls. But the code ships in the host service, and any desktop client triggers it.
- **Transcripts.** Native, in WSL2 `~/.claude/projects/...jsonl` and `~/.codex/sessions/...`, plus Superset's own PTY scrollback ring.
