**Credential-handling policy risk (7.16b).** These are the cases where Archon itself handles vendor credentials:
- **Codex `auth.json` copy.** `archon setup` reads `~/.codex/auth.json` (`tryReadCodexAuth`) and asks "Found existing Codex auth at ~/.codex/auth.json. Use it?". On yes, it writes the id, access and refresh tokens and the account id into Archon's `.env` as `ARCHON_CODEX_*`. In Docker, the entrypoint runs `setup-auth`, which "Creates ~/.codex/auth.json from environment variables" inside the container so the unmodified binary can run. The tokens stay on the user's machine: A3 is unaffected, and F1 is PARTIAL at most for Codex. OpenAI: "App-server authentication has never been permitted for commercial or hosted services." Sources: R/packages/cli/src/commands/setup.ts#L435-L436, #L889-L893, #L1624-L1627; R/packages/server/src/scripts/setup-auth.ts#L1-L5; R/docker-entrypoint.sh#L124-L126.
- **Its own OAuth logins, with client impersonation.**
  - Claude: Archon's login uses Claude Code's OAuth client ID (`9d1c250a-…`) and Claude Code's scope `user:sessions:claude_code`.
  - ChatGPT: Archon's login uses the Codex CLI's client ID with `originator=pi`.
  - Both logins store refresh and access tokens in Archon's vault (`~/.archon/credential-key`).
  - Anthropic: "developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." The authorization step does run on claude.ai, but Archon collects and stores the resulting tokens.
  - No reads of `~/.claude/.credentials.json`, the keychain, or usage endpoints were found. Nor were any spoofed user-agents.
- **Docker and Claude.** "`CLAUDE_USE_GLOBAL_AUTH=true` does not work in Docker (no local `claude` CLI). Provide `CLAUDE_CODE_OAUTH_TOKEN` or `CLAUDE_API_KEY` explicitly." (D/reference/security.md#L192). A user-minted `claude setup-token` token is the 7.6 injected-token row.

## Deep-dive

Checked 2026-10-19 by deepdive-archon against tag v0.12.1 (`R/` and `D/` prefixes as above); `dev` HEAD `a7acc54` read where noted. Configuration assumed throughout (7.16c), which the stack must document:
- the native Linux binary plus both provider plugins installed in WSL2;
- `claude /login` and `codex login` done in WSL2;
- Archon's own Anthropic and ChatGPT logins never connected, and Pi not used on a ChatGPT plan;
- `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_API_KEY`, `ANTHROPIC_API_KEY` and `CODEX_API_KEY` unset. Any of the first three switches Claude to "explicit" auth, and an API key bills the API (R/packages/providers/src/claude/provider.ts#L211-L215);
- `archon setup`'s offer to copy `~/.codex/auth.json` into `.env` declined;
- no container isolation.

### Harness integration (from source)
- **How it invokes `claude`.**
  - `@anthropic-ai/claude-agent-sdk` `query()` with `pathToClaudeCodeExecutable` set to the user's installed `claude` in compiled builds (the SDK-bundled binary in source installs).
  - Options: `permissionMode: 'bypassPermissions'`, `allowDangerouslySkipPermissions: true`, `systemPrompt` = the `claude_code` preset plus optional append (unless a node sets `systemPrompt:`), `settingSources` = project and user, `includeHookEvents: true`, and Archon tool-capture hooks.
  - The bypass mode is fixed: "Archon runs the Claude Code SDK in `bypassPermissions` mode … without interactive confirmation prompts". Approvals cannot be turned back on per tool; governance is through workflow gates and attention waits.
  - Sources: R/packages/providers/src/claude/provider.ts#L942-L990 ; D/reference/security.md#L36-L53.
- **How it invokes `codex`.**
  - One `codex app-server` process per turn (`spawner(binary.path, ['app-server', ...])`), JSON-RPC `initialize`, then `thread/start` or `thread/resume`/`thread/fork` with `cwd`, `sandbox: 'danger-full-access'`, `approvalPolicy: 'never'`, and config limited to sandbox/network/web-search/MCP/skills.
  - Node instructions are prepended to the user prompt.
  - Sources: R/packages/providers/src/codex/app-server.ts#L211-L227 ; R/packages/providers/src/codex/provider.ts#L721-L731 ; R/packages/providers/src/codex/provider.ts#L1255-L1300.
- **OAuth credentials.**
  - Default path: none. Claude and Codex read their own stores.
  - Opt-in paths the stack must avoid: Archon's own Anthropic and ChatGPT OAuth (Claude Code and Codex CLI client IDs, tokens vaulted, delivered as `CLAUDE_CODE_OAUTH_TOKEN` or app-server `chatgptAuthTokens`), and the `archon setup` copy of `auth.json` into `.env`.
  - See the "Credential-handling policy risk (7.16b)" note above.
- **Where transcripts land.**
  - WSL2 `~/.claude/projects/<worktree-path>/<session>.jsonl`.
  - `~/.codex/sessions/…`.
  - Archon's own `~/.archon/workspaces/<owner>/<repo>/logs/<run>.jsonl`.
  - Provider events in the Archon DB.

### Stack fit
- **Covers:** orchestrator and client/UI (web console, chat adapters) for both harnesses, with first-class cross-harness delegation and child-run lineage.
- **Topology on the user's PC:**
  - Archon's Linux binary and provider plugins in WSL2, with `claude` and `codex` installed and logged in there.
  - `archon serve` (foreground) wrapped in a systemd user service. WSL itself must be kept running.
  - The console on `:3090` (binds `0.0.0.0`).
  - The phone reaches it through Tailscale on the Windows host, via WSL mirrored networking or `tailscale serve` → `localhost:3090`. The tailwind file flags issue #9228 (502s from Windows Serve to WSL2).
  - Web auth must be enabled (form auth or Caddy basic auth), because "Authentication is optional" on solo installs and `/api/*` is otherwise open on the network.
  - The Docker install is weaker: no global auth for Claude ("does not work in Docker"), so a `setup-token` must be injected, and Codex auth is seeded from env.
- **Needs from partners:**
  - **A5 (required).** No partner fits cleanly. GitHub Mobile shows committed state only (PARTIAL). Obsidian Sync cannot open `\\wsl$` vaults, while Archon wants WSL2 workspaces. Tailscale's Taildrive is alpha, and SMB is UNKNOWN. Orca and T3 Code have phone file browsers but are full orchestrators of their own.
  - **Networking (A1 reach, F6).** Tailscale.
  - **Full-fidelity transcripts on the phone (A2 iPhone, A6b viewer).** agentsview with `require_auth`.
  - **F10.** No partner fixes it while Archon runs in WSL2.
- **Conflicts and risks:**
  - Agents always run with approvals bypassed (Claude `bypassPermissions`, Codex `danger-full-access` and `never`).
  - The chat bots answer anyone when their allow-lists are empty.
  - Archon's worktree path-lock covers only Archon runs, so other tools editing the same checkout can collide.
  - The WSL2 homes are separate from the Windows homes used by claude-desktop and chatgpt-desktop-codex. Logins, sessions and `/resume` lists are not shared.
  - N2 rests on a single release published by a second human (see Open questions).

### Deep-dive open questions

## Open questions
- **Does an offered but unused claude.ai login fail the Claude path?** The question is whether that alone fails A3 for the Claude path when the user runs Global Auth (`claude /login`) and never connects a subscription in Archon. Happy's `happy connect` was scoped out explicitly ("the stack must be able to avoid them"); Archon's scope has no such carve-out, so this screen applies 7.6/7.16b as written. A ruling that the path is avoidable would move A3 (Claude) to PASS and the screen to PASS. So would Archon removing or gating the #3925 Anthropic OAuth, or an Anthropic approval for Archon (none found). The stricter alternative (7.16b strict) fails the Claude path in any case.
- **Can Archon be used only for Codex?** If Archon stays in a stack only for Codex while Claude Code comes from another component, does the platform-level login offer still count against the stack? This is decided at Stage 4. Either way, the stack must also avoid the Archon-owned ChatGPT login and Pi-on-ChatGPT paths.
- **Does the console work on an actual iPhone or iPad?** It has not been checked on a device. The code has a viewport tag and a narrow-screen drawer (#3402), but no doc claims phone support, and the adapters page steers mobile users to Slack and Telegram. - **How is the server reached and protected?** The WSL2-hosted server must be reachable from the phone (Tailscale, or WSL mirrored networking plus a port rule), and auth is off on solo installs. Neither is solved inside Archon. This matters for A1 at stack level, and for security, because `/api/*` is open when web auth is off.
